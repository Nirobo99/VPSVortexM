Промт для Этапа 0: Фундамент и окружение

Привет, Cascade! Мы начинаем разработку мессенджера VortexyM согласно нашему Техническому заданию (ТЗ).

Текущий этап: Этап 0 – Фундамент и окружение.

Цель этапа: настроить среду разработки, поднять базы данных (PostgreSQL, Redis) через Docker, создать базовую структуру backend (Node.js/Express) и frontend (React/Vite), реализовать модели пользователей и базовую аутентификацию (регистрация, вход, JWT).

Важно: все команды и файлы создавай пошагово. После каждого значимого изменения мы будем тестировать. Используй лучшие практики безопасности: пароли хешировать (bcrypt), секреты хранить в .env, не коммитить .env в git.

План действий (подзадачи):

1. Создание структуры проекта

· Создай в корне папки: server, client.
· В папке server инициализируй npm-пакет (npm init -y).
· Установи необходимые зависимости: express, cors, dotenv, sequelize, pg, pg-hstore, redis, jsonwebtoken, bcrypt, socket.io.
· Установи nodemon как dev-зависимость.
· В корне проекта создай файл .gitignore (исключи node_modules, .env, dist, build).

2. Docker-окружение

· Создай в корне файл docker-compose.yml с сервисами:
  · postgres (образ postgres:15, БД vortexym, пользователь vortexym_user, пароль vortexym_pass, порт 5432).
  · redis (образ redis:7, порт 6379).
· Добавь volumes для сохранения данных.
· Напиши краткую инструкцию по запуску контейнеров (docker-compose up -d).

3. Настройка backend

· В папке server создай файл .env с переменными:
  ```
  PORT=3001
  DB_NAME=vortexym
  DB_USER=vortexym_user
  DB_PASSWORD=vortexym_pass
  DB_HOST=localhost
  DB_PORT=5432
  REDIS_HOST=localhost
  REDIS_PORT=6379
  JWT_SECRET=супер_секретный_ключ_измени_меня
  ```
· Создай файл server/app.js – базовый Express с middleware (cors, json).
· Создай файл server/server.js – запуск сервера на порту из .env.
· Добавь скрипты в package.json: "start": "node server.js", "dev": "nodemon server.js".

4. Подключение к базам данных

· Создай папку server/models.
· В server/models/index.js настрой подключение к PostgreSQL через Sequelize (используй переменные окружения).
· Создай файл server/utils/redis.js для подключения к Redis (используй redis клиент).
· Проверь подключения при старте сервера (логируй успех или ошибку).

5. Создание модели User

· В server/models/User.js определи модель User с полями:
  · id (integer, primaryKey, autoIncrement)
  · email (string, unique, allowNull false)
  · passwordHash (string, allowNull false)
  · name (string, allowNull false)
  · avatar (string, defaultValue: 'default-avatar.png')
  · birthYear (integer, allowNull false) – для проверки при регистрации
  · role (enum: 'user', 'admin', defaultValue: 'user')
  · stickerLimit (integer, defaultValue: 5)
  · invisible (boolean, defaultValue: false)
  · invisibleExpiry (date, allowNull true)
  · hidden (boolean, defaultValue: false) – для скрытых профилей (пригодится позже)
  · anonymous (boolean, defaultValue: false) – для анонимных профилей
· Добавь timestamps: true.
· Экспортируй модель из models/index.js.

6. Регистрация и вход (JWT)

· Создай папку server/routes и файл auth.js.
· В auth.js:
  · POST /register:
    · Принимает email, password, name, birthYear.
    · Хеширует пароль (bcrypt, salt rounds 10).
    · Создаёт пользователя в БД.
    · Возвращает успех (201).
  · POST /login:
    · Принимает email, password.
    · Ищет пользователя, сравнивает пароль.
    · Если верно, создаёт JWT (срок действия, например, 7 дней) и возвращает его.
· Подключи маршруты в app.js по пути /api/auth.
· Создай middleware server/middleware/auth.js, который проверяет JWT и добавляет пользователя в req.user.

7. Базовая защита и тестирование

· Добавь rate limiting для входа (например, 5 попыток за 15 минут) – можно использовать express-rate-limit или самодельный на Redis (отложим на потом, но заложим основу).
· Убедись, что все секреты в .env, а сам .env добавлен в .gitignore.
· Протестируй ручки через Postman или curl (можно написать простой тест в будущем).

8. Инициализация frontend (заготовка)

· В папке client выполни npm create vite@latest . -- --template react.
· Установи зависимости: axios, socket.io-client, react-router-dom, i18next, react-i18next.
· Создай базовую структуру: src/components, src/pages, src/services (api), src/i18n (для будущей локализации).
· Настрой прокси для разработки, чтобы запросы к API шли на backend (в vite.config.js добавить proxy).

9. Фиксация изменений

· После завершения всех шагов, сделай коммит в git с сообщением: "feat: этап 0 – фундамент и окружение".

Примечание: Пиши код последовательно, не перескакивай. Если что-то непонятно, спрашивай. После выполнения каждого пункта останавливайся и жди моего подтверждения (я буду говорить "дальше"). Давай начнём с создания структуры проекта и файла .gitignore.



Промт для Этапа 1: Пользователи и профили


---

Привет, Cascade! Продолжаем разработку мессенджера VortexyM. Мы успешно завершили Этап 0 (фундамент). Теперь переходим к Этапу 1: Пользователи и профили.

Цель этапа: реализовать все функции, связанные с пользовательским профилем, кроме стикеров и платных услуг. Это включает расширение модели пользователя, редактирование профиля, публичный/приватный режим, чёрный список, кастомизацию (темы), регистрацию с дополнительными вопросами (год животного и математический пример) с блокировкой на 24 часа, защиту от брутфорса, а также создание базовой админ-панели для просмотра пользователей.

Важно: все изменения должны быть безопасными, использовать уже настроенные механизмы (JWT, Redis, Sequelize). Код должен быть хорошо структурирован, с комментариями.

План действий (подзадачи):

1. Расширение модели User

· Добавь в модель User (файл server/models/User.js) недостающие поля (некоторые уже есть, проверь и дополни):
  · birthYear (integer, allowNull false) – уже должно быть.
  · role (enum: 'user', 'admin', defaultValue: 'user') – уже есть.
  · avatar (string, defaultValue: 'default-avatar.png') – уже есть.
  · stickerLimit (integer, defaultValue: 5) – уже есть.
  · invisible (boolean, defaultValue: false) – уже есть.
  · invisibleExpiry (date, allowNull true) – уже есть.
  · Добавь поле bio (text) – краткая информация о пользователе.
  · Добавь поле isPublic (boolean, defaultValue: true) – публичный или приватный профиль.
  · Добавь поле theme (string, defaultValue: 'light') – для кастомизации темы (light/dark/custom).
  · Добавь поле customColors (json, defaultValue: null) – для хранения пользовательских цветов (если нужна тонкая настройка).
· Выполни синхронизацию модели с БД (sequelize.sync). Можно использовать alter: true в server.js (уже должно быть).

2. Редактирование профиля (API)

· Создай новый маршрут в server/routes/users.js (или добавь в auth.js, но лучше выделить).
· Реализуй PUT /api/users/profile – обновление данных профиля (name, bio, avatar, isPublic, theme, customColors).
  · Доступно только авторизованным пользователям (проверка JWT).
  · Валидация входных данных.
  · Обновление записи в БД.
· Реализуй GET /api/users/me – получение данных текущего пользователя (для отображения профиля).
· Реализуй GET /api/users/:id – получение публичной информации о другом пользователе (если профиль публичный).
  · Если профиль приватный, возвращать только базовую информацию (имя, аватар) или ошибку доступа.

3. Публичный/приватный режим профиля

· При запросе профиля другого пользователя проверяй поле isPublic.
· Если профиль приватный и запрашивающий не является владельцем, возвращай ограниченные данные (например, только имя и аватар) или статус 403.

4. Чёрный список (BlockedUser)

· Создай модель BlockedUser в server/models/BlockedUser.js:
  · id (integer, primaryKey)
  · userId (integer, foreign key to User) – кто блокирует
  · blockedUserId (integer, foreign key to User) – кого блокируют
  · createdAt (date)
· Установи связи: User.hasMany(BlockedUser, as 'blockedUsers', foreignKey 'userId').
· Реализуй API для чёрного списка:
  · POST /api/users/block/:userId – добавить пользователя в чёрный список.
  · DELETE /api/users/block/:userId – удалить из чёрного списка.
  · GET /api/users/block/list – получить список заблокированных.
· При отправке сообщения, создании чата и т.д. (в будущих этапах) нужно будет проверять, не заблокирован ли получатель.

5. Кастомизация профиля (темы, цвета)

· На клиенте (фронтенд) нужно будет реализовать интерфейс для выбора темы и настройки цветов, но пока сосредоточимся на бэкенде.
· Убедись, что поля theme и customColors сохраняются и возвращаются в API профиля.

6. Регистрация с дополнительными вопросами и блокировка на 24 часа

· Модифицируй эндпоинт POST /api/auth/register:
  · Добавь в тело запроса поля: birthYear (уже должно быть), animalAnswer, mathAnswer.
  · На сервере создай словарь (объект) соответствия годов животным, например:
    ```javascript
    const animalMap = {
      1990: 'Лошадь',
      1991: 'Овца',
      1992: 'Обезьяна',
      1993: 'Петух',
      1994: 'Собака',
      1995: 'Свинья',
      1996: 'Крыса',
      1997: 'Бык',
      1998: 'Тигр',
      1999: 'Кролик',
      2000: 'Дракон',
      2001: 'Змея',
      // ... можно продолжить
    };
    ```
  · Проверь animalAnswer: должно совпадать с animalMap[birthYear]. Если нет – ошибка.
  · Проверь mathAnswer: правильный ответ на пример "2+2*2" = 6. Если ответ не 6 – ошибка.
  · При любой ошибке (неправильный ответ на любой вопрос):
    · Запиши в Redis ключ blocked:email:<email> с TTL 24 часа (86400 секунд).
    · Запиши в Redis ключ blocked:ip:<ip_адрес> (получи IP из req.ip или req.headers['x-forwarded-for']) тоже с TTL 24 часа.
    · Верни ошибку 400 с сообщением "Неверные ответы на контрольные вопросы. Регистрация заблокирована на 24 часа."
  · Перед началом регистрации проверяй, нет ли таких ключей в Redis. Если есть – возвращай ошибку о блокировке.
· Обнови документацию API.

7. Защита от брутфорса (ограничение попыток входа)

· Добавь middleware для rate limiting на эндпоинт /api/auth/login.
· Используй Redis для хранения счётчика попыток:
  · Ключ: login:attempts:ip:<ip>.
  · При каждой неудачной попытке увеличивай счётчик и устанавливай TTL, например, 15 минут.
  · Если счётчик превышает 5, возвращай ошибку "Слишком много попыток. Попробуйте позже."
· При успешном входе удаляй ключ.

8. Базовая админ-панель (просмотр пользователей)

· Создай отдельную группу маршрутов для админа в server/routes/admin.js.
· Добавь middleware isAdmin, который проверяет req.user.role === 'admin'.
· Реализуй GET /api/admin/users – получение списка всех пользователей (с пагинацией).
  · Доступно только админам.
  · Возвращай основные поля (id, email, name, role, birthYear, createdAt и т.д.).
· Для тестирования можно вручную установить роль admin у какого-либо пользователя через БД.
· (Опционально) Добавь простой интерфейс на фронтенде для просмотра списка пользователей (отдельная страница /admin/users), но сейчас можно ограничиться бэкендом.

9. Интеграция с фронтендом (минимально)

· На клиенте создай страницу профиля (/profile), где пользователь может просматривать и редактировать свои данные (имя, bio, аватар, настройки приватности, тему).
· Создай страницу регистрации с дополнительными полями (год рождения, животное, математический пример).
· Добавь обработку ошибок от сервера (блокировка и т.п.).
· Добавь страницу входа с обработкой rate limiting.
· Создай сервис api.js для вызовов к бэкенду с использованием axios и JWT.

10. Фиксация изменений

· После завершения всех шагов, сделай коммит в git с сообщением: "feat: этап 1 – пользователи и профили (регистрация с вопросами, чёрный список, админка)".

Примечание: как и раньше, выполняй шаги последовательно, после каждого значимого шага сообщай мне о выполнении. Если нужна помощь с конкретным куском кода – спрашивай. Давай начнём с расширения модели User и создания API для редактирования профиля.



Промт для Этапа 2: Личные сообщения и реальное время

---

Привет, Cascade! Продолжаем разработку мессенджера VortexyM. Этап 1 (Пользователи и профили) завершён. Теперь переходим к Этапу 2: Личные сообщения и реальное время.

Цель этапа: создать полноценный функционал личных сообщений (диалогов) между пользователями с поддержкой реального времени (WebSockets), отправкой текста, голосовых сообщений, видеосообщений (кружочков), файлов, а также реализовать «умные» функции: редактирование/удаление, ответы, реакции, закреплённые сообщения, пересылку, поиск по сообщениям.

Технические детали:

· Бэкенд: Node.js/Express, Socket.IO для реального времени.
· База данных: PostgreSQL (модели Message, Attachment, Reaction и др.), Redis (для статусов онлайн, непрочитанных счётчиков).
· Фронтенд: React, Socket.IO-client, обработка медиа (запись audio/video, загрузка файлов).

Важно: учитывать ограничения из ТЗ (например, чёрный список должен блокировать отправку сообщений). Все действия должны быть безопасными, проверять авторизацию и права.

План действий (подзадачи):

1. Модели данных для сообщений

· Создай модель Message в server/models/Message.js со следующими полями:
  · id (integer, primaryKey)
  · senderId (integer, foreign key to User, not null)
  · receiverId (integer, foreign key to User, not null) – для личных сообщений получатель
  · text (text) – текст сообщения, может быть null, если только медиа
  · type (enum: 'text', 'voice', 'video', 'file', 'image') – тип сообщения
  · status (enum: 'sent', 'delivered', 'read') – статус доставки
  · replyToId (integer, foreign key to Message, allowNull) – если это ответ на другое сообщение
  · forwardedFromId (integer, foreign key to User, allowNull) – если переслано от кого-то
  · isEdited (boolean, default: false)
  · isDeleted (boolean, default: false) – для мягкого удаления
  · deletedAt (date, allowNull) – если удалено
  · createdAt, updatedAt
· Создай модель Attachment для файлов:
  · id (integer)
  · messageId (foreign key to Message)
  · url (string) – путь к файлу
  · type (enum: 'image', 'voice', 'video', 'file')
  · size (integer) – размер в байтах
  · duration (integer, allowNull) – для аудио/видео (длительность в секундах)
· Создай модель Reaction:
  · id (integer)
  · messageId (foreign key to Message)
  · userId (foreign key to User)
  · emoji (string) – например, '👍', '❤️'
· Создай модель PinnedMessage (для закреплённых сообщений в диалоге):
  · id (integer)
  · userId (foreign key to User) – для какого пользователя закреплено (в личных сообщениях закреплённые сообщения индивидуальны)
  · messageId (foreign key to Message)
  · (В будущем для бесед/каналов понадобится другая логика, но пока для личных)

2. Настройка Socket.IO на сервере

· В файле server/server.js (или отдельном socket.js) инициализируй Socket.IO с CORS для клиента.
· При подключении клиента аутентифицируй пользователя через JWT (можно передавать токен в handshake).
· Сохраняй соответствие socket.id ↔ userId в Redis (или в памяти, но Redis лучше для масштабирования).
· Реализуй базовые события:
  · connection – логирование, добавление в онлайн.
  · disconnect – удаление из онлайн.
· Добавь возможность подписки на события определённого диалога (позже).

3. API для сообщений (HTTP)

· Создай маршруты в server/routes/messages.js:
  · GET /api/messages/:userId – получение истории сообщений с конкретным пользователем (с пагинацией, сортировка по дате).
    · Проверка: не заблокирован ли пользователь (через чёрный список).
    · Возвращать список сообщений с вложениями, реакциями.
  · POST /api/messages – отправка нового сообщения (текст, тип, replyToId, forwardedFromId).
    · Если есть файлы, сначала загрузить их на сервер (см. пункт 4).
    · Создать запись в БД.
    · После сохранения отправить событие через Socket.IO получателю (если он онлайн).
    · Вернуть созданное сообщение.
  · PUT /api/messages/:id – редактирование текста сообщения (только для своих сообщений, не старше, например, 24 часа).
    · Установить isEdited: true.
  · DELETE /api/messages/:id – удаление сообщения (мягкое удаление, установить isDeleted: true, deletedAt).
    · Для всех участников диалога сообщение должно отображаться как удалённое.
  · POST /api/messages/:id/reactions – добавить/удалить реакцию (передавать emoji; если уже есть такая реакция от этого пользователя – удалить).
  · POST /api/messages/:id/pin – закрепить сообщение (для текущего пользователя).
  · DELETE /api/messages/:id/pin – открепить.

4. Загрузка файлов (голосовые, видео, изображения, документы)

· Создай маршрут POST /api/upload (или в составе отправки сообщения мультипарт).
· Используй multer для обработки загрузки.
· Настрой хранилище: локальная папка uploads/ (позже можно заменить на S3 или CDN).
· Для видео и аудио можно использовать ffmpeg для получения длительности, создания превью (опционально).
· Для изображений можно создавать уменьшенные копии (thumbnails).
· После успешной загрузки верни URL файла и метаданные (размер, тип, длительность).
· В сообщении сохраняй ссылку на файл в поле text? Лучше создать запись в Attachment и связать с сообщением.

5. Реальное время: новые сообщения и статусы

· При отправке сообщения (POST /api/messages) после сохранения в БД:
  · Получить список сокетов получателя из Redis (по userId).
  · Отправить событие new_message с данными сообщения (включая отправителя, вложения).
  · Если получатель не в онлайне, сообщение будет доставлено при следующем подключении (через историю).
· Реализуй событие message_status для обновления статуса прочтения:
  · Когда пользователь открывает диалог, клиент отправляет событие mark_read с ID последнего прочитанного сообщения.
  · Сервер обновляет статусы всех сообщений в этом диалоге до read для этого пользователя.
  · Оповещает отправителя через событие message_status (чтобы у него отобразились галочки).
· Для статуса "доставлено" (delivered) можно считать, что сообщение доставлено, если получатель онлайн и мы отправили ему событие; если офлайн – доставлено будет позже.

6. Чёрный список и ограничения

· В middleware для маршрутов сообщений проверяй, не заблокировал ли отправитель получателя или наоборот.
· Если заблокировано – возвращай ошибку 403.
· Также при отправке события через Socket.IO проверяй блокировку (на всякий случай).

7. Умные функции на клиенте (React)

· Создай компонент ChatWindow для отображения диалога с конкретным пользователем.
· Используй useEffect для загрузки истории сообщений и подписки на Socket.IO события.
· Реализуй:
  · Отправку текстовых сообщений.
  · Запись голосовых сообщений (используй MediaRecorder API).
  · Запись видеосообщений (кружочки) – захват видео с камеры, запись, отправка.
  · Загрузку файлов (drag-and-drop, выбор файла).
  · Отображение вложений (изображения превью, аудиоплеер, видеоплеер).
  · Редактирование своих сообщений (по клику, появляется поле ввода).
  · Удаление сообщений.
  · Реакции (выбор эмодзи, отображение существующих).
  · Ответы на сообщения (цитирование).
  · Пересылку сообщений (кнопка "переслать", выбор диалога).
  · Закреплённые сообщения (отображаются вверху чата).
  · Поиск по сообщениям в диалоге (строка поиска).
· Для работы с медиа используй библиотеки: react-media-recorder (упрощает запись), ffmpeg.wasm (для обработки на клиенте, если нужно).

8. Поиск по сообщениям

· Реализуй на сервере эндпоинт GET /api/messages/search?q=текст&withUserId=... (возможно, с пагинацией).
· Используй Op.iLike в Sequelize для поиска по тексту.
· Вернуть найденные сообщения с подсказками.

9. Непрочитанные счётчики

· В Redis храни для каждого пользователя количество непрочитанных сообщений от каждого собеседника.
· При отправке сообщения увеличивай счётчик для получателя.
· При открытии диалога и отметке прочитанных – обнуляй счётчик для этого собеседника.
· Отображай на клиенте в списке диалогов количество непрочитанных.

10. Интеграция с фронтендом: список диалогов

· Создай компонент DialogsList, который получает список последних диалогов пользователя.
· Для этого нужен эндпоинт GET /api/dialogs:
  · Группирует сообщения по собеседнику, возвращает последнее сообщение, непрочитанный счётчик, данные собеседника (имя, аватар).
· Обновляй список в реальном времени через Socket.IO (например, событие dialogs_updated).

11. Тестирование и отладка

  · Отправка сообщения онлайн-пользователю – должно прийти мгновенно.
  · Отправка офлайн-пользователю – при заходе он получает историю и счётчик.

Промт для Этапа 3: Аудио/видеозвонки

---

Привет, Cascade! Мы успешно завершили Этап 2 (Личные сообщения и реальное время). Теперь переходим к Этапу 3: Аудио/видеозвонки.

Цель этапа: реализовать функционал аудио- и видеозвонков между пользователями, а также групповых звонков. В соответствии с ТЗ, звонки должны быть доступны как в личных диалогах, так и в групповых чатах (беседах). Для групповых звонков необходимо использовать SFU-решение (например, LiveKit, Jitsi или Mediasoup), чтобы обеспечить качественную передачу видео при множестве участников. Также нужно предусмотреть запись звонков с обязательным уведомлением участников и хранение записей. Для анонимных профилей (созданных через страницу Моргенштерн@) необходимо реализовать маскировку лица (размытие) и искажение голоса при звонках; пока можно сделать заглушку, но заложить архитектуру для последующей реализации.

Технические детали:

· Сервер: Node.js/Express, Socket.IO (уже используется для сообщений), интеграция с выбранным SFU.
· SFU: рекомендуется LiveKit (open-source, хорошая документация, поддержка WebRTC) или Jitsi. Выбор за вами, но нужно обосновать.
· Клиент: React, библиотеки для работы с WebRTC (livekit-client, jitsi-meet или простой RTCPeerConnection).
· База данных: модели для хранения информации о звонках (история, записи).
· Безопасность: проверка прав (могут ли пользователи звонить друг другу, не заблокированы ли), аутентификация через JWT.

План действий (подзадачи):

1. Выбор и настройка SFU-сервера

· Исследуй варианты: LiveKit, Jitsi, Mediasoup.
· Предложи оптимальный вариант для нашего проекта (критерии: простота интеграции, масштабируемость, открытый код, поддержка групповых звонков, возможность записи).
· Установи выбранный SFU (например, LiveKit) – можно в Docker контейнере рядом с PostgreSQL и Redis.
· Настрой переменные окружения для подключения к SFU (API ключи, URL).

2. Модели данных для звонков

· Создай модель Call в server/models/Call.js:
  · id (integer, primaryKey)
  · roomName (string, unique) – идентификатор комнаты (генерируется на сервере)
  · initiatorId (integer, foreign key to User) – кто начал звонок
  · type (enum: 'audio', 'video')
  · isGroup (boolean) – групповой или личный
  · status (enum: 'pending', 'active', 'ended', 'missed')
  · startedAt (date)
  · endedAt (date)
· Создай модель CallParticipant:
  · id
  · callId (foreign key to Call)
  · userId (foreign key to User)
  · joinedAt (date)
  · leftAt (date)
  · isMuted (boolean) – опционально, для состояния
· Создай модель CallRecording:
  · id
  · callId (foreign key to Call)
  · url (string) – путь к записи
  · size (integer)
  · duration (integer) – длительность записи
  · createdAt

3. API для управления звонками (HTTP + WebSockets)

· Создай маршруты в server/routes/calls.js:
  · POST /api/calls/start – инициировать звонок.
    · Принимает targetId (для личного) или conversationId (для группового), type ('audio'/'video').
    · Проверяет возможность звонка (не заблокированы ли пользователи, существует ли беседа и т.д.).
    · Генерирует уникальное имя комнаты (например, call_<uuid>).
    · Создаёт запись в Call со статусом 'pending'.
    · Возвращает данные комнаты (roomName, токен доступа к SFU, если требуется).
    · Через Socket.IO отправляет событие incoming_call целевым пользователям (с информацией о звонке).
  · POST /api/calls/:callId/accept – принять звонок.
    · Обновляет статус звонка на 'active', добавляет участника в CallParticipant.
    · Возвращает обновлённые данные комнаты.
    · Оповещает инициатора через Socket.IO, что звонок принят.
  · POST /api/calls/:callId/reject – отклонить звонок.
    · Обновляет статус на 'missed' (или 'ended').
    · Оповещает инициатора.
  · POST /api/calls/:callId/end – завершить звонок (любой участник).
    · Устанавливает endedAt, статус 'ended'.
    · Для всех участников закрывает комнату (если используется SFU, там своё управление).
    · Оповещает всех участников о завершении.
  · GET /api/calls/history – получить историю звонков текущего пользователя (с пагинацией).
· Интеграция с Socket.IO:
  · При incoming_call отправлять событие конкретному пользователю (по его сокету).
  · При call_accepted, call_rejected, call_ended – соответствующие события.

4. Интеграция с SFU (на примере LiveKit)

· Установи пакеты: livekit-server-sdk (для создания токенов на сервере), livekit-client (на клиенте).
· На сервере создай утилиту для генерации токенов доступа к комнатам LiveKit.
  · Токен должен содержать identity (userId) и название комнаты.
  · Используй API ключ и секрет из переменных окружения.
· При старте звонка (POST /calls/start) генерируй токен для инициатора и возвращай его вместе с URL LiveKit-сервера.
· При accept – генерируй токен для принимающего.
· При завершении звонка – комната в LiveKit может быть закрыта автоматически, если нет участников.

5. Клиентская часть (React) – компоненты звонков

· Создай компонент CallNotification – всплывающее окно при входящем звонке (отображается в любом месте приложения). Содержит информацию: кто звонит, тип (аудио/видео), кнопки "Принять", "Отклонить".
· Создай страницу/компонент CallScreen – полноэкранный интерфейс для активного звонка.
  · Используй livekit-client для подключения к комнате, отображения видео участников.
  · Реализуй элементы управления: отключение микрофона, отключение камеры, завершение звонка, переключение между аудио/видео.
  · Для групповых звонков – сетка видео (или активный спикер).
· Интеграция с Socket.IO:
  · При получении события incoming_call показывать CallNotification.
  · При нажатии "Принять" отправлять запрос на сервер и переходить на CallScreen.
  · При нажатии "Отклонить" – отправлять reject.
· Обработка состояния звонка: если пользователь уже в звонке, новые входящие звонки могут отклоняться автоматически (или ставиться в ожидание).

6. Запись звонков

· Настрой запись в LiveKit (если поддерживается) или используй отдельный сервис.
· При старте звонка, если запись разрешена (в будущем можно сделать настройку), включай запись.
· Уведомление участников: перед началом записи показывать модальное окно "Звонок будет записан" с согласием (по ТЗ обязательно уведомление). Если кто-то отказывается – запись не включается или звонок не начинается.
· После завершения звонка файл записи сохраняется (LiveKit может сохранять в S3 или локально). Сохраняем ссылку в CallRecording.
· Добавь API для получения списка записей и их прослушивания/просмотра.

7. Маскировка для анонимных профилей (заглушка)

· Для анонимных профилей (поле anonymous: true) необходимо модифицировать видео- и аудиопотоки перед отправкой.
· Пока реализуй заглушку: при звонке с анонимного профиля на клиенте применяй простые эффекты (например, наложение размытия на видео через CSS-фильтры, искажение голоса через Web Audio API). Это временное решение.
· В будущем этот функционал можно будет улучшить (серверная обработка или более сложные клиентские эффекты).
· Убедись, что для анонимных профилей в интерфейсе звонка не отображается их реальная информация (имя всегда "Анонимный участник").

8. Интеграция с групповыми беседами

· В компоненте группового чата добавь кнопку "Начать звонок" (аудио/видео).
· При нажатии вызывается API /calls/start с conversationId.
· Сервер должен проверить, что пользователь является участником беседы.
· Далее аналогично личным звонкам, но целевые пользователи – все участники беседы (кроме инициатора). Им рассылается incoming_call с указанием группы.
· Групповые звонки должны поддерживать до 500 участников (согласно лимитам бесед). SFU должен справляться с такой нагрузкой (LiveKit поддерживает до сотен участников).

9. Безопасность и проверки

· Проверка блокировок: перед звонком убедись, что ни одна из сторон не заблокировала другую.
· Проверка прав доступа: для групповых звонков только участники беседы могут звонить и присоединяться.
· Rate limiting на создание звонков (чтобы избежать спама).

10. Тестирование

· Протестируй личные аудио/видеозвонки между двумя пользователями.
· Протестируй групповые звонки с несколькими участниками.
· Проверь запись звонков и уведомление.
· Убедись, что при блокировке пользователя звонки невозможны.
· Протестируй маскировку для анонимных профилей (хотя бы визуально).

11. Фиксация изменений

· После завершения этапа сделай коммит: "feat: этап 3 – аудио/видеозвонки (LiveKit, запись, маскировка)".

Примечание: Начнём с выбора SFU и установки LiveKit. После этого – модели данных и базовый API. Как всегда, выполняй шаги последовательно, после каждого значимого этапа сообщай о готовности. Если нужна помощь с конкретными частями (например, генерация токенов LiveKit) – спрашивай.



Промт для Этапа 4: Каналы

---

Привет, Cascade! Мы успешно завершили Этап 3 (Аудио/видеозвонки). Теперь переходим к Этапу 4: Каналы.

Цель этапа: реализовать функционал публичных и закрытых каналов. Каналы — это инструмент для создания сообществ (как Telegram-каналы). Владелец канала может публиковать посты, управлять подписчиками, назначать администраторов, монетизировать контент (платные подписки, товары), проводить опросы, создавать мероприятия и т.д. В соответствии с ТЗ, каналы могут быть публичными (доступны всем) или закрытыми (доступ по ссылке-приглашению или запросу). Также предусмотрена верификация каналов (галочка) с предоставлением документов.

Технические детали:

· Используем уже существующие модели: User, Message (возможно, пригодится для комментариев, но пока посты будут отдельной моделью).
· Новые модели: Channel, ChannelMember, Post, Product, Poll, PollOption, Event, ChannelInviteLink, VerificationRequest (для каналов).
· API должно быть защищено JWT, права доступа проверяются на основе ролей в канале (владелец, администратор, подписчик).
· Для массовых рассылок и уведомлений используем Socket.IO (если нужно оповещать подписчиков в реальном времени).
· Для загрузки медиа в посты используем уже созданный механизм загрузки файлов (из Этапа 2).

План действий (подзадачи):

1. Модели данных для каналов

· Создай модель Channel в server/models/Channel.js:
  · id (integer, primaryKey)
  · name (string, not null)
  · description (text)
  · avatar (string, default: 'default-channel.png')
  · type (enum: 'public', 'private') – публичный или закрытый
  · slug (string, unique) – читаемая ссылка (например, @channelname)
  · inviteLink (string, unique) – для закрытых каналов ссылка-приглашение (генерируется автоматически)
  · ownerId (integer, foreign key to User)
  · isVerified (boolean, default: false) – есть ли галочка
  · verificationRequestId (integer, foreign key to VerificationRequest, allowNull) – связь с заявкой
  · settings (json) – дополнительные настройки (например, скрывать ли администраторов, разрешено ли комментировать и т.д.)
  · createdAt, updatedAt
· Создай модель ChannelMember для участников канала:
  · id
  · channelId (foreign key to Channel)
  · userId (foreign key to User)
  · role (enum: 'owner', 'admin', 'member') – владелец, администратор, подписчик
  · permissions (json) – для администраторов можно хранить индивидуальные права (например, может ли публиковать посты, управлять подписчиками и т.д.)
  · joinedAt (date)
  · isBlocked (boolean, default: false) – заблокирован ли пользователь в канале
· Создай модель Post (пост в канале):
  · id
  · channelId (foreign key to Channel)
  · authorId (foreign key to User) – кто создал пост
  · title (string, optional)
  · content (text)
  · type (enum: 'text', 'media', 'poll', 'event', 'product') – тип поста
  · media (json) – массив ссылок на прикреплённые файлы (или отдельная модель Attachment, переиспользовать)
  · isPinned (boolean, default: false) – закреплён ли пост вверху канала
  · isPaid (boolean, default: false) – платный ли пост (pay-per-view)
  · price (float, allowNull) – цена за просмотр (если isPaid)
  · views (integer, default: 0) – счётчик просмотров
  · createdAt, updatedAt
· Создай модель Product (товар, продаваемый в канале):
  · id
  · channelId (foreign key to Channel)
  · name (string)
  · description (text)
  · price (float)
  · currency (string, default: 'RUB')
  · images (json) – массив ссылок на фото
  · isActive (boolean, default: true)
  · createdAt, updatedAt
· Создай модель Poll (опрос):
  · id
  · postId (foreign key to Post) – если опрос привязан к посту
  · question (string)
  · multipleChoice (boolean, default: false) – можно ли выбирать несколько вариантов
  · isAnonymous (boolean, default: false) – анонимное голосование
  · endsAt (date, allowNull) – дата окончания
· Создай модель PollOption (вариант ответа в опросе):
  · id
  · pollId (foreign key to Poll)
  · text (string)
  · votes (integer, default: 0) – количество голосов (можно обновлять триггером)
· Создай модель Vote (голос пользователя):
  · id
  · pollId (foreign key to Poll)
  · userId (foreign key to User)
  · optionId (foreign key to PollOption)
  · createdAt
· Создай модель Event (мероприятие):
  · id
  · channelId (foreign key to Channel)
  · title (string)
  · description (text)
  · startTime (date)
  · endTime (date)
  · location (string) – онлайн или оффлайн (можно ссылка)
  · image (string)
· Создай модель ChannelInviteLink (для управления ссылками-приглашениями):
  · id
  · channelId (foreign key to Channel)
  · link (string, unique) – уникальный идентификатор
  · createdBy (foreign key to User)
  · expiresAt (date, allowNull)
  · maxUses (integer, allowNull) – максимальное количество использований
  · uses (integer, default: 0) – сколько раз использована
  · isActive (boolean, default: true)
· Создай модель VerificationRequest (заявка на верификацию канала):
  · id
  · channelId (foreign key to Channel)
  · userId (foreign key to User) – кто подал заявку (владелец)
  · documents (json) – массив ссылок на загруженные документы (фото паспорта, документы компании)
  · description (text) – описание причины
  · status (enum: 'pending', 'approved', 'rejected')
  · reviewedBy (foreign key to User, allowNull) – админ, который рассмотрел
  · reviewedAt (date)
  · createdAt, updatedAt

2. API для управления каналами

· Создай маршруты в server/routes/channels.js (и подключи в app.js).
· Реализуй следующие эндпоинты:
  · Создание канала: POST /api/channels
    · Принимает name, description, type ('public'/'private'), avatar (опционально).
    · Создаёт запись в Channel, автоматически генерирует slug (например, из названия, транслитерация).
    · Создаёт запись в ChannelMember для создателя с ролью 'owner'.
    · Возвращает созданный канал.
  · Получение канала по slug или id: GET /api/channels/:slug
    · Доступен всем, но для закрытых каналов нужно проверять, является ли пользователь участником (иначе возвращать только基本信息: название, описание, аватар, но не посты).
  · Редактирование канала: PUT /api/channels/:id
    · Доступно владельцу и администраторам с соответствующими правами.
    · Можно менять название, описание, аватар, тип, настройки (settings).
    · Если меняется тип с private на public, можно сгенерировать новый inviteLink (или оставить старый).
  · Удаление канала: DELETE /api/channels/:id
    · Только владелец.
    · Каскадно удалить все связанные записи (посты, участники и т.д.) или пометить как удалённые.
  · Получение списка каналов пользователя: GET /api/users/me/channels
    · Возвращает каналы, где пользователь является участником (с ролью).
  · Поиск публичных каналов: GET /api/channels?q=... – поиск по названию и описанию (только публичные).

3. Управление участниками и администраторами

· Подписка на канал (вступление):
  · Для публичного: POST /api/channels/:id/join – добавляет пользователя в ChannelMember с ролью 'member'.
  · Для закрытого: нужна ссылка-приглашение. POST /api/channels/join/:inviteLink – проверяет ссылку, увеличивает счётчик использований, добавляет участника.
· Выход из канала: DELETE /api/channels/:id/leave – удаляет пользователя из участников (или помечает как удалённого).
· Назначение/снятие администраторов: PUT /api/channels/:id/admins
  · Только для владельца.
  · Принимает userId и массив прав (permissions). Добавляет/обновляет запись в ChannelMember, меняя роль на 'admin' и устанавливая permissions.
· Блокировка/разблокировка пользователя: POST /api/channels/:id/block/:userId и DELETE аналогично.
  · Устанавливает isBlocked: true в ChannelMember.
  · Заблокированный пользователь не может просматривать канал (даже если он участник).
· Скрытие администрации: в настройках канала (settings.hideAdmins) – при включении не показывать список администраторов обычным участникам.

4. Посты

· Создание поста: POST /api/channels/:id/posts
  · Доступно владельцу и администраторам с правом публикации.
  · Принимает title (опц.), content, type, media (массив файлов), isPaid, price (если платный).
  · Если тип 'poll', нужно также передать данные опроса (вопрос, варианты).
  · Если тип 'event', передать данные события.
  · Если тип 'product', передать данные товара (но для товаров, возможно, отдельный эндпоинт).
  · Создаёт запись в Post, а также связанные записи (Poll, Event, Product).
· Получение постов канала: GET /api/channels/:id/posts
  · Пагинация, сортировка по дате.
  · Доступно всем участникам канала (для закрытых – только участникам).
· Редактирование поста: PUT /api/posts/:id
  · Доступно автору, владельцу канала, администраторам с правом редактирования.
· Удаление поста: DELETE /api/posts/:id
  · Аналогично.
· Закрепление/открепление поста: POST /api/posts/:id/pin и DELETE.
  · Только владелец или администратор.
· Просмотр поста (увеличение счётчика): GET /api/posts/:id – увеличивает views.

5. Опросы

· При создании поста с типом 'poll' создаётся опрос.
· Голосование: POST /api/polls/:id/vote
  · Принимает optionId (или массив, если multipleChoice).
  · Проверяет, не голосовал ли уже пользователь (если не multipleChoice).
  · Увеличивает счётчик в PollOption и создаёт запись в Vote.
· Результаты опроса: GET /api/polls/:id/results – возвращает статистику голосов.

6. Товары

· Создание товара: POST /api/channels/:id/products
  · Доступно владельцу/админам.
  · Принимает name, description, price, images.
· Получение товаров канала: GET /api/channels/:id/products
· Покупка товара: POST /api/products/:id/buy
  · Будет интегрировано с платежами позже, пока заглушка (возвращает успех).

7. Массовая рассылка

· POST /api/channels/:id/broadcast
  · Доступно владельцу/админам.
  · Принимает message (текст), media (опционально).
  · Отправляет уведомление всем подписчикам канала:
    · Через Socket.IO, если они онлайн.
    · Также можно создать системное сообщение или уведомление в интерфейсе.
    · В будущем – сохранять в отдельную таблицу уведомлений.

8. Упоминания (@username, @all)

· При создании поста или комментария (если будут) нужно парсить текст на наличие упоминаний.
· Если найдено @username – найти пользователя по username (нужно добавить поле username в модель User, уникальное) и отправить ему уведомление (через Socket.IO или сохранить).
· Если найдено @all – отправить уведомление всем подписчикам канала.

9. Верификация канала (галочка)

· Подача заявки: POST /api/channels/:id/verification-request
  · Только владелец канала.
  · Принимает documents (массив файлов), description.
  · Создаёт запись в VerificationRequest со статусом 'pending'.
· Просмотр заявок (админка): GET /api/admin/verification-requests (позже, сейчас можно сделать простой эндпоинт).
· Рассмотрение заявки: PUT /api/admin/verification-requests/:id
  · Принимает status ('approved'/'rejected'), comment (опц.).
  · Если одобрено, устанавливает isVerified: true у канала.
· После одобрения рядом с названием канала отображается галочка (на клиенте).

10. Интеграция с клиентом (React)

· Создай страницу канала (/channel/:slug), которая отображает:
  · Информацию о канале (название, описание, аватар, количество подписчиков).
  · Кнопку подписки/отписки (в зависимости от статуса).
  · Ленту постов (с возможностью пагинации).
  · Для владельца/админов – кнопки управления (редактировать канал, создать пост, управление участниками, настройки).
  · Отображение галочки, если канал верифицирован.
· Создай компонент создания поста (форма с текстом, загрузкой медиа, выбором типа).
· Создай компонент опроса (отображение вариантов, голосование).
· Создай компонент товара (карточка, кнопка купить).
· Создай страницу списка каналов пользователя (в профиле).

11. Тестирование

· Протестируй создание канала, вступление, публикацию постов.
· Проверь права доступа: обычный участник не может публиковать посты, администратор с правами может.
· Проверь закрытые каналы: вход по ссылке-приглашению.
· Проверь опросы: голосование, результаты.
· Проверь массовую рассылку (пока через логи).
· Проверь верификацию: создание заявки, одобрение.

12. Фиксация изменений

· После завершения этапа сделай коммит: "feat: этап 4 – каналы (посты, опросы, товары, верификация)".

Примечание: как обычно, выполняй шаги последовательно. Начни с создания моделей, затем базовые CRUD для каналов, потом посты и остальное. Если нужны уточнения – спрашивай.



Промт для Этапа 5: Беседы (групповые чаты)

---

Привет, Cascade! Мы успешно завершили Этап 4 (Каналы). Теперь переходим к Этапу 5: Беседы (групповые чаты).

Цель этапа: реализовать функционал групповых чатов (бесед) с ограничением количества участников, возможностью расширения лимита за разовую плату, а также функции управления для владельцев и администраторов (аналогично каналам, но с акцентом на чат). Беседы могут быть публичными (открытое вступление) или закрытыми (по ссылке-приглашению или запросу). Участники могут общаться в чате, отправлять сообщения, голосовые, видеосообщения (кружочки), файлы. Владельцы и администраторы имеют дополнительные возможности: редактирование беседы, создание постов/объявлений, монетизация, товары, массовая рассылка, блокировка участников, передача прав, удаление беседы, настройка ограничений и т.д.

Технические детали:

· Используем существующие модели: User, Message (адаптируем для групповых чатов), Attachment, Reaction, Product (переиспользуем), Poll (возможно), Event (возможно).
· Новые модели: Conversation (беседа), ConversationMember (участники с ролями), ConversationInviteLink (ссылки-приглашения), ConversationPurchase (история покупок расширений), Announcement (посты/объявления) – или будем использовать специальный тип сообщения.
· API должно быть защищено JWT, права доступа проверяются на основе ролей в беседе (owner, admin, member).
· Для расширения лимита используем заглушку платежей (позже интеграция), но логика увеличения maxParticipants должна быть реализована.
· Счётчик свободных мест должен отображаться для владельцев/админов.

План действий (подзадачи):

1. Модели данных для бесед

· Создай модель Conversation в server/models/Conversation.js:
  · id (integer, primaryKey)
  · name (string, not null)
  · description (text)
  · avatar (string, default: 'default-conversation.png')
  · type (enum: 'public', 'private') – публичная или закрытая
  · ownerId (integer, foreign key to User)
  · maxParticipants (integer, default: 500) – текущий лимит участников
  · settings (json) – дополнительные настройки:
    · hideAdmins (boolean) – скрывать ли список администраторов
    · restrictions – объект с ограничениями (запрет медиа, премодерация, ограничение по времени для новых участников)
  · createdAt, updatedAt
· Создай модель ConversationMember:
  · id
  · conversationId (foreign key to Conversation)
  · userId (foreign key to User)
  · role (enum: 'owner', 'admin', 'member')
  · permissions (json) – для администраторов (например, может ли приглашать, удалять сообщения, публиковать объявления)
  · joinedAt (date)
  · isBlocked (boolean, default: false)
  · mutedUntil (date, allowNull) – до какого времени отключены уведомления
· Создай модель ConversationInviteLink (аналогично каналам):
  · id
  · conversationId (foreign key to Conversation)
  · link (string, unique)
  · createdBy (foreign key to User)
  · expiresAt (date)
  · maxUses (integer)
  · uses (integer, default: 0)
  · isActive (boolean, default: true)
· Создай модель ConversationPurchase для отслеживания покупок расширения:
  · id
  · conversationId (foreign key to Conversation)
  · userId (foreign key to User) – кто купил (владелец или админ)
  · package (enum: '100', '500') – какой пакет
  · amount (integer) – количество мест (100 или 500)
  · price (float) – цена (250 или 999)
  · purchasedAt (date)
  · paymentId (string) – для связи с платёжной системой (позже)
· Модификация модели Message для поддержки бесед:
  · Добавь поля: conversationId (foreign key to Conversation, allowNull) – если сообщение относится к беседе (для личных сообщений это поле null, а receiverId не null).
  · Для личных сообщений оставляем receiverId, для групповых – conversationId. Остальные поля (senderId, text, type, attachments и т.д.) остаются.
  · Обнови индексы для быстрого поиска.

2. API для управления беседами

· Создай маршруты в server/routes/conversations.js (подключи в app.js).
· Создание беседы: POST /api/conversations
  · Принимает name, description, type ('public'/'private'), avatar (опционально).
  · Создаёт запись в Conversation, добавляет создателя в ConversationMember с ролью 'owner'.
  · Возвращает созданную беседу.
· Получение беседы: GET /api/conversations/:id
  · Доступно только участникам (проверка членства).
  · Возвращает информацию о беседе, включая настройки, список участников (с ролями), счётчик свободных мест (для владельцев/админов).
· Редактирование беседы: PUT /api/conversations/:id
  · Доступно владельцу и администраторам с правом редактирования.
  · Можно менять название, описание, аватар, тип, настройки.
· Удаление беседы: DELETE /api/conversations/:id
  · Только владелец.
  · Каскадно удалить все связанные записи (участники, сообщения, ссылки, покупки).
· Получение списка бесед пользователя: GET /api/users/me/conversations
  · Возвращает все беседы, где пользователь является участником, с последним сообщением, количеством непрочитанных и т.д.

3. Управление участниками

· Вступление в публичную беседу: POST /api/conversations/:id/join
  · Проверяет, не превышен ли лимит (maxParticipants). Если да – возвращает ошибку с предложением купить расширение (для владельца/админов это не должно мешать им вступать? Владелец уже участник).
  · Добавляет пользователя в ConversationMember с ролью 'member'.
  · Оповещает других участников через Socket.IO (событие new_member).
· Вступление по ссылке-приглашению: POST /api/conversations/join/:link
  · Находит ссылку, проверяет активность, лимит использований, срок действия.
  · Аналогично добавляет участника.
· Выход из беседы: DELETE /api/conversations/:id/leave
  · Удаляет пользователя из участников (или помечает как удалённого).
  · Если это был владелец, нужно передать права другому (пока не реализовано, можно запретить выход владельцу, если есть другие участники, или автоматически передавать права).
· Назначение/снятие администраторов: PUT /api/conversations/:id/admins
  · Только для владельца.
  · Принимает userId и массив прав (permissions). Обновляет запись в ConversationMember (роль 'admin', permissions).
· Блокировка/разблокировка пользователя: POST /api/conversations/:id/block/:userId и DELETE аналогично.
  · Устанавливает isBlocked: true в ConversationMember. Заблокированный не может писать сообщения, просматривать историю (по сути, исключается).
· Передача прав владения: PUT /api/conversations/:id/transfer
  · Только владелец.
  · Принимает newOwnerId (должен быть администратором или участником). Меняет роль текущего владельца на 'admin' (или 'member') и новому владельцу ставит 'owner'.

4. Расширение лимита участников

· Получение информации о лимите: В GET /api/conversations/:id для владельцев/админов возвращать maxParticipants, currentParticipants (количество участников), freeSlots (свободные места).
· Покупка расширения: POST /api/conversations/:id/purchase-slot
  · Доступно владельцу и администраторам (с правом на покупку? пока только владелец).
  · Принимает package ('100' или '500').
  · Проверяет, есть ли уже купленные пакеты (можно хранить историю, но логика простая: увеличиваем maxParticipants на соответствующее количество).
  · Создаёт запись в ConversationPurchase (пока без реальной оплаты, просто заглушка, paymentId можно пропустить).
  · Возвращает новый лимит и сообщение об успехе.
· Важно: Если лимит достигнут, при попытке вступления нового участника (или приглашения) сервер должен возвращать ошибку с кодом 403 и специальным сообщением: "Достигнут лимит участников группового чата". На клиенте это сообщение должно отображаться с ссылкой "Увеличить лимит" (для владельцев/админов).
· Для обычных участников при достижении лимита показывать просто "Чат переполнен".

5. Сообщения в беседе

· Поскольку мы адаптировали модель Message, можно переиспользовать существующие эндпоинты для сообщений, но нужно учесть, что для бесед receiverId не используется, вместо него conversationId.
· Создай новые эндпоинты или модифицируй существующие (например, GET /api/messages?conversationId=... для получения истории сообщений беседы).
· Отправка сообщения в беседу: POST /api/conversations/:id/messages
  · Аналогично отправке личного сообщения, но с conversationId.
  · Проверяет, не заблокирован ли пользователь в этой беседе.
  · Сохраняет сообщение, обрабатывает вложения.
  · Через Socket.IO отправляет событие new_message всем участникам беседы (кроме отправителя).
· Редактирование, удаление, реакции, ответы – всё аналогично личным сообщениям, но с учётом прав (администраторы могут удалять чужие сообщения? В ТЗ это не указано, но можно добавить как опцию в настройках).
· Получение истории сообщений: GET /api/conversations/:id/messages с пагинацией.

6. Посты/объявления в беседе

· В ТЗ указано "создание постов/записей" для владельцев/админов. Это могут быть специальные сообщения, которые выделяются (например, закрепляются вверху) и не теряются в потоке. Можно реализовать через отдельную модель Announcement:
  · id, conversationId, authorId, title (опц.), content, media (json), createdAt, updatedAt.
· API:
  · POST /api/conversations/:id/announcements – создать объявление (доступно админам/владельцу).
  · GET /api/conversations/:id/announcements – получить список объявлений (доступно всем участникам).
  · PUT/DELETE – редактирование/удаление (только автор или админ).
· Альтернативно можно использовать специальный тип сообщения (type: 'announcement') и помечать его, но тогда сложнее с правами на создание. Решай сам. Для простоты предлагаю создать отдельную модель.

7. Монетизация и товары в беседах

· Модель Product уже есть, нужно добавить поле conversationId (foreign key to Conversation), чтобы товары можно было привязывать к беседе.
· Создай эндпоинты:
  · POST /api/conversations/:id/products – создание товара (админы/владелец).
  · GET /api/conversations/:id/products – список товаров.
  · POST /api/products/:id/buy – покупка (заглушка).
· Аналогично можно добавить поддержку опросов (Poll) для бесед, привязав к conversationId.

8. Массовая рассылка

· POST /api/conversations/:id/broadcast
  · Доступно владельцу/админам.
  · Принимает message (текст), media (опционально).
  · Отправляет уведомление всем участникам беседы (через Socket.IO или создаёт системные сообщения). Можно создать специальное сообщение от имени "Система" или от администратора, но с пометкой, что это рассылка.
  · Лучше всего создать запись в Message с типом 'broadcast' и отправить её всем (но тогда будет много одинаковых сообщений). Или просто разослать уведомления без сохранения в историю. По ТЗ, вероятно, это должны быть сообщения, которые видят все. Поэтому создадим одно сообщение в беседе от имени отправителя, но с пометкой (например, жирный текст) что это объявление. Это проще: просто создать обычное сообщение, но для всех оно будет как обычное. Однако массовая рассылка подразумевает, что оно будет доставлено всем, даже если они не в сети? Лучше создать системное уведомление в отдельной таблице Notification, но пока можно отложить. Для простоты предлагаю пока не реализовывать сложную рассылку, а просто использовать обычное сообщение, которое увидят все, кто зайдут в чат. В будущем можно улучшить.

9. Упоминания (@username, @all)

· При создании сообщения (текстового) парсить его на наличие @username. Если найдено – найти пользователя с таким username (нужно добавить поле username в модель User, уникальное, генерировать при регистрации).
· Отправить уведомление упомянутому пользователю (через Socket.IO событие mention).
· Если найдено @all – отправить уведомление всем участникам беседы (осторожно, чтобы не спамить, можно ограничивать частоту).

10. Настройка ограничений

· В модели Conversation есть поле settings.restrictions. Реализуй API для его обновления (PUT /api/conversations/:id/settings).
· Ограничения могут включать:
  · disableMedia (boolean) – запрет на отправку медиа (изображения, видео, файлы). Тогда при попытке отправить медиа возвращать ошибку.
  · newMemberRestriction (object) – например, muteForMinutes – новые участники не могут писать в течение N минут.
  · premoderation (boolean) – сообщения новых участников сначала отправляются на проверку админам (сложно, можно отложить).
· Проверяй эти ограничения в middleware при отправке сообщения.

11. Скрытие администрации

· В settings.hideAdmins – если true, то при запросе списка участников (для обычных участников) не показывать, кто является администратором (все отображаются как участники). Для владельца и самих админов список должен показываться полностью.

12. Интеграция с клиентом (React)

· Создай страницу беседы (/conversation/:id), которая отображает:
  · Информацию о беседе (название, описание, аватар, количество участников).
  · Для владельцев/админов – кнопки управления (редактировать, пригласить, настройки, купить расширение).

  · Окно чата с историей сообщений (аналогично личным сообщениям).
  · Поле ввода сообщения с поддержкой медиа.
· Создай компонент для отображения счетчика свободных мест (только для владельцев/админов) в шапке беседы. При достижении лимита показывать сообщение и кнопку "Увеличить лимит", которая открывает модальное окно с выбором пакета.
· Реализуй модальное окно покупки расширения с двумя вариантами (100 мест за 250р, 500 за 999р). При нажатии "Купить" отправлять запрос на сервер, после успеха обновлять интерфейс.
· Добавь возможность создавать пригласительные ссылки (для закрытых бесед) в интерфейсе управления.
· Для обычных участников: если они пытаются зайти в закрытую беседу, показывать сообщение о необходимости приглашения.

13. Тестирование

· Протестируй создание беседы, добавление участников (через join и по ссылке).
· Проверь лимит: попробуй добавить 501-го участника – должно появиться сообщение о достижении лимита (для админа). Для обычного участника просто ошибка.

· Проверь отправку сообщений, медиа, реакций – всё должно работать как в личных сообщениях.
· Проверь настройки ограничений (например, запрет медиа).

· Создай middleware или сервисы для проверки доступа к платным функциям:

  · Невидимка: проверяем наличие активной подписки типа 'invisible' (где endDate > now). Если есть – в профиле выставляем invisible: true, иначе false. При входе проверяем подписку и обновляем поле (можно через cron или при каждом запросе).
  · Расширение беседы: в модели Conversation есть maxParticipants. При покупке пакета увеличиваем это поле и создаём запись в ConversationPurchase. Проверка лимита при добавлении новых участников.
  · Премиум-подписка: активная подписка типа 'premium'. Проверяем её наличие и предоставляем соответствующие привилегии (невидимка автоматически, увеличенный лимит стикеров – например, +20 к базовому лимиту, отключение рекламы – на клиенте проверяем флаг и не показываем рекламу).
  · Платные стикерпаки: проверяем наличие записи в UserProduct для соответствующего productId. Если есть – показываем стикеры в интерфейсе.

  · Платные посты (pay-per-view): проверяем, есть ли запись о покупке этого поста пользователем (нужна модель PostPurchase). Если нет – не показываем контент, а показываем кнопку "Купить за N руб".

4. API для покупок и подписок

· Создай маршруты в server/routes/payments.js.
· Создание платежа (общая логика): POST /api/payments/create
  · Принимает productType (например, 'sticker_pack', 'invisible_sub', 'conversation_slot', 'premium_sub', 'post_purchase'), productId (ID конкретного товара, пакета или поста), metadata (доп. данные, например, conversationId для расширения).
  · В зависимости от типа определяет цену, создаёт запись в Payment со статусом 'pending', генерирует ссылку на оплату через платёжную систему (или возвращает данные для клиента, чтобы инициировать оплату).
  · Возвращает paymentId, confirmationUrl (для редиректа) или clientSecret (для Stripe).
· Webhook для уведомлений: POST /api/payments/webhook (публичный эндпоинт, доступен без аутентификации).
  · Проверяет подпись запроса (используя секрет из .env).
  · Изменяет статус соответствующего Payment на 'succeeded' или 'failed'.
  · При успешной оплате вызывает функцию handleSuccessfulPayment(payment), которая:
    · Определяет тип продукта из metadata.
    · Выполняет соответствующее действие (увеличивает лимит стикеров, активирует подписку, увеличивает maxParticipants, создаёт запись в UserProduct и т.д.).
    · Если есть бонусный счёт и покупка совершена за бонусы (позже), списывает бонусы.
  · При неуспешной – помечает как failed.
· Получение истории платежей пользователя: GET /api/payments/history – возвращает список платежей текущего пользователя.

5. Реализация конкретных платных функций

5.1. Пакеты стикеров

5.2. Функция «Невидимка» (ежемесячная подписка)

· Создай продукт для подписки: { type: 'subscription', name: 'Невидимка', price: 15, metadata: { subscriptionType: 'invisible', periodMonths: 1 } }.
· При успешной оплате:
  · Найти или создать активную подписку типа 'invisible' для пользователя.
  · Установить startDate = now(), endDate = now() + 1 месяц, status = 'active'.

· Для автоматического продления (если платёжка поддерживает) нужно будет обрабатывать webhook от платёжной системы о продлении. Пока можно сделать без авто-продления (ручное каждый месяц).

5.3. Расширение лимита бесед

· Создай продукты:
  · Пакет +100 мест: { type: 'conversation_slot', name: '+100 мест в беседе', price: 250, metadata: { slots: 100 } }
  · Пакет +500 мест: цена 999, slots: 500
· При успешной оплате: в metadata должен быть conversationId. Найти беседу, увеличить maxParticipants на количество slots, создать запись в ConversationPurchase.

5.4. Премиум-подписка

· Создай продукт: { type: 'subscription', name: 'Премиум', price: XXX (нужно определить), metadata: { subscriptionType: 'premium', periodMonths: 1 } }.
· Включи в неё набор привилегий:
  · Невидимка (автоматически активируется на время подписки).
  · Увеличенный лимит стикеров: например, +20 к базовому лимиту (можно реализовать как виртуальное поле: effectiveStickerLimit = baseLimit + (isPremium ? 20 : 0)).
  · Отключение рекламы (на клиенте проверять наличие премиум-подписки и не показывать рекламу).
  · Приоритетная поддержка (просто пометка в профиле).
  · Расширенная аналитика для каналов (будет реализовано в админке позже).
· При активации премиум-подписки также активируем невидимку (создаём запись в Subscription типа 'invisible' с тем же сроком действия или просто при проверке невидимки учитываем премиум-статус). Лучше второе: при проверке req.user.isInvisible() проверять либо отдельную подписку, либо премиум.

5.7. Платные посты (pay-per-view)

· Добавь модель PostPurchase:
  · id
  · postId (foreign key to Post)
  · userId (foreign key to User)
  · purchasedAt (date)
· При создании поста в канале можно указать isPaid: true и price.
· API для покупки поста: POST /api/posts/:id/purchase
  · Создаёт платёж (через общий механизм) с типом 'post_purchase'.
  · После успешной оплаты создаёт запись в PostPurchase.
· При получении поста (GET /api/posts/:id):
  · Если пост платный, проверить, есть ли запись в PostPurchase для текущего пользователя. Если нет – вернуть только превью (например, первые 100 символов) и информацию о цене, но не полный контент.
  · Если есть – вернуть полный пост.

5.8. Реферальная программа

· При регистрации нового пользователя можно проверять, пришёл ли он по реферальной ссылке. Для этого нужно передавать параметр ref (ID пригласившего) при регистрации.
· Создай эндпоинт для генерации реферальной ссылки: GET /api/referral/link – возвращает уникальную ссылку с кодом (можно использовать ID пользователя + соль).
· При успешной регистрации с реферальным кодом создаём запись в Referral со статусом 'pending'.
· Назначь целевое действие для активации реферала: например, первая покупка или просто подтверждение email. Выбери: первая покупка (тогда при первой успешной оплате реферала начисляем бонус пригласившему).
· При достижении цели:
  · Начисляем бонус на счёт пригласившего (создаём BonusTransaction с типом 'referral_bonus' и увеличиваем баланс).
  · Обновляем статус реферала на 'active', bonusPaid = true.
· Размер бонуса можно задать в конфиге (например, 10% от первой покупки или фиксированная сумма 50 руб). Лучше фиксированная сумма, чтобы не усложнять.
· Бонусы можно тратить на платные функции. Для этого в процессе оплаты нужно предусмотреть возможность частичной или полной оплаты бонусами (создавать комбинированный платёж). Это сложно, пока можно сделать просто: при покупке, если у пользователя достаточно бонусов, можно полностью оплатить бонусами (тогда не создаётся платёж в платёжной системе, а просто списываются бонусы и активируется функция). Добавим позже, а пока можно просто накапливать бонусы и потом выводить (админ вручную). Но по ТЗ бонусы можно тратить, значит, надо реализовать.
  · Создай эндпоинт POST /api/payments/with-bonus – аналогично созданию платежа, но с флагом useBonus: true. Проверяет баланс, списывает бонусы и сразу активирует функцию (без реальной оплаты). Если не хватает – возвращает ошибку.

6. Реклама

· Для показа рекламы пользователям с бесплатным аккаунтом (без премиум-подписки):
  · На клиенте при инициализации приложения проверять статус пользователя (есть ли премиум).
  · Если нет – в нужных местах (например, в боковой панели, над списком чатов) показывать рекламные баннеры.
· Для управления рекламой в админке (этап 7) мы создадим интерфейс для добавления баннеров, настройки таргетинга. Пока можно сделать простую заглушку: один статический баннер.
· Нативная реклама в каналах: владельцы каналов могут разрешить показ рекламы в своих каналах и получать процент. Это сложная система, можно отложить на потом. Но заложим модель ChannelAd:
  · id
  · channelId (foreign key to Channel)
  · advertiserId (foreign key to User) – кто размещает рекламу
  · content (json) – баннер или текст
  · impressions (integer) – сколько показов куплено
  · price (float) – цена
  · status (enum: 'active', 'paused', 'ended')
  · startDate, endDate
· Позже реализуем API для покупки рекламы в каналах.

7. Интеграция с клиентом (React)

· Создай страницу/компонент PricingPlans, где отображаются все доступные платные функции с ценами и описанием.
· Для каждой функции кнопка "Купить" / "Подключить". При нажатии вызывается соответствующий API для создания платежа, пользователь перенаправляется на страницу оплаты.
· Для подписок отображать статус (активна до ...) и возможность отключить автопродление (если реализовано).
· Для пакетов стикеров показывать текущий лимит и сколько осталось свободных мест.
· Для расширения бесед – на странице беседы (для владельцев/админов) показывать счётчик мест и кнопку "Увеличить лимит".
· Добавь страницу бонусного счёта, где виден баланс и история транзакций, а также возможность пополнить бонусы (если предусмотрен вывод, но пока не надо).
· Реферальная программа: страница со ссылкой для приглашения, статистикой (сколько пригласил, сколько бонусов начислено).
· Настройки рекламы: показывать рекламу только бесплатным пользователям, для премиум – скрывать.

8. Тестирование

· Используй тестовые ключи платёжной системы (sandbox).
· Протестируй все сценарии покупок: успешная оплата, отмена, неуспешная.
· Проверь, что после успешной оплаты соответствующие лимиты и подписки активируются.
· Проверь реферальную программу: создай двух пользователей, перейди по ссылке, соверши покупку, убедись, что бонус начислен.
· Проверь оплату бонусами (если реализовано).
· Проверь, что реклама показывается только бесплатным пользователям.

9. Фиксация изменений

Примечание: начни с выбора платёжной системы и настройки моделей. Затем поэтапно реализуй каждую платную функцию. Помни о безопасности: все webhook-и должны проверять подпись, секреты не должны попадать в код. Если нужны уточнения – спрашивай.



Промт для Этапа 7: Админ-панель (расширенная)

---

Привет, Cascade! Мы успешно завершили Этап 6 (Платежи и монетизация). Теперь переходим к Этапу 7: Админ-панель (расширенная).

Цель этапа: создать полноценную административную панель для управления проектом. Админ-панель должна быть доступна по отдельному URL (например, /admin) и только для пользователей с ролью admin или owner. Владелец проекта (Валерий Оборин) имеет неограниченные права, а также может назначать других администраторов с ограниченными правами (например, только модерация жалоб, только управление пользователями и т.д.). В админ-панели должны быть реализованы следующие функции (согласно ТЗ):

· Полное редактирование площадки (название, логотип, основные настройки).
· Включение/выключение проекта (сайт полностью недоступен для пользователей, кроме админов).
· Массовая рассылка (внутри проекта и по email).
· Редактирование статических страниц (О нас, Правила, Контакты) через встроенный редактор.
· Создание рекламы и рекламных блоков (баннеры, настройка таргетинга).
· Аналитика: количество пользователей, статистика чатов/каналов, доходы, графики активности.
· Настройка платежей: управление тарифами (цены на стикеры, расширение бесед, подписки), просмотр транзакций.
· Управление пользователями: просмотр списка, поиск, редактирование профилей, блокировка/разблокировка (в том числе по IP), удаление пользователей, обработка заявок на получение галочки (пользователи и каналы).
· Управление жалобами (система жалоб на сообщения, каналы, пользователей) – просмотр, принятие мер (предупреждение, блокировка, удаление контента).
· Управление платными функциями: включение/отключение, изменение цен.
· Объявления на площадке: текст, время показа, отображение у всех пользователей в верхней части.
· Назначение администраторов проекта (только для владельца) с настройкой прав доступа к разделам админки.
· Логирование действий администраторов для аудита (кто, когда, что сделал).
· Регулярное резервное копирование базы данных и файлов (с возможностью восстановления) – настройка периодичности, ручной запуск.
· Также в админ-панель должны быть интегрированы функции просмотра и обработки заявок на верификацию (из Этапа 4 – каналы) и, возможно, заявки на верификацию пользователей (из Этапа 1).

Технические детали:

· Используем существующие модели: User, Channel, VerificationRequest, Payment, Subscription, Product, Complaint (новую), AdminLog (новую), SiteSettings (новую), AdBlock (новую), Backup (новую) и т.д.
· API должно быть защищено middleware, проверяющим роль admin или owner. Для владельца – полный доступ, для админов – доступ только к разрешённым разделам (права хранятся в модели AdminPermission).
· Интерфейс админ-панели – отдельная часть приложения (например, отдельный набор страниц в React), доступная по маршруту /admin. Можно использовать готовые UI-библиотеки (например, Ant Design, Material-UI) для ускорения разработки.
· Безопасность: все действия админов должны логироваться, критические операции (удаление, блокировка) требовать подтверждения.

План действий (подзадачи):

1. Модели данных для админ-панели

· Создай модель SiteSettings для хранения глобальных настроек площадки (должна быть одна запись):
  · id (integer, default: 1)
  · siteName (string, default: 'VortexyM')
  · logoUrl (string)
  · faviconUrl (string)
  · registrationEnabled (boolean, default: true)
  · maintenanceMode (boolean, default: false) – соответствует включению/выключению проекта
  · maintenanceMessage (text) – сообщение, показываемое пользователям при выключении
  · defaultLanguage (string, default: 'ru')
  · contactEmail (string)
  · socialLinks (json) – ссылки на соцсети
  · updatedAt
· Создай модель Admin (или расширь User полем isAdmin, но для хранения прав нужна отдельная модель):
  · userId (foreign key to User, primary key)
  · role (enum: 'owner', 'admin') – owner может всё, admin имеет ограниченные права
  · permissions (json) – массив разрешённых разделов/действий, например:
    ```json
    ["users.view", "users.edit", "users.block", "complaints.view", "complaints.resolve", "analytics.view"]
    ```
· Создай модель AdminLog:
  · id
  · adminId (foreign key to User)
  · action (string) – описание действия, например "Заблокировал пользователя 123"
  · targetType (string) – тип объекта: 'user', 'channel', 'post', 'complaint' и т.д.
  · targetId (integer)
  · details (json) – дополнительные данные (старое значение, новое значение)
  · ip (string) – IP адрес администратора
  · createdAt
· Создай модель Complaint (жалоба):
  · id
  · complainantId (foreign key to User) – кто жалуется
  · targetType (enum: 'user', 'message', 'channel', 'post')
  · targetId (integer) – ID объекта жалобы
  · reason (enum: 'spam', 'abuse', 'illegal', 'other') – причина
  · description (text)
  · status (enum: 'pending', 'resolved', 'rejected') – статус рассмотрения
  · resolvedBy (foreign key to User, allowNull) – администратор, который рассмотрел
  · resolution (text) – комментарий администратора
  · createdAt, updatedAt
· Создай модель AdBlock (рекламный блок):
  · id
  · name (string)
  · type (enum: 'banner', 'native') – тип
  · content (json) – например, для баннера: { imageUrl, linkUrl, altText }
  · placement (string) – место размещения (например, 'sidebar', 'top', 'feed')
  · targeting (json) – настройки таргетинга (например, { country: ['RU'], notSubscribed: true })
  · status (enum: 'active', 'paused')
  · impressions (integer, default: 0) – сколько раз показан
  · clicks (integer, default: 0)
  · startDate (date)
  · endDate (date, allowNull)
  · createdAt, updatedAt
· Создай модель Backup:
  · id
  · filename (string)
  · size (integer) – размер в байтах
  · type (enum: 'manual', 'scheduled') – тип создания
  · status (enum: 'pending', 'completed', 'failed')
  · url (string) – ссылка для скачивания (если хранится в облаке)
  · createdAt
· Создай модель StaticPage (для редактируемых страниц):
  · id
  · slug (string, unique) – например, 'about', 'terms', 'privacy'
  · title (string)
  · content (text) – HTML или Markdown (можно использовать редактор)
  · updatedAt
· Создай модель Announcement (объявление на площадке):
  · id
  · text (string)
  · type (enum: 'info', 'warning', 'success') – для стилизации
  · startAt (date)
  · endAt (date)
  · isActive (boolean) – можно включать/отключать вручную
  · createdBy (foreign key to User)
  · createdAt, updatedAt

2. Базовая структура админ-панели на бэкенде

· Создай папку server/routes/admin и внутри неё файлы для каждого раздела:
  · adminAuth.js – проверка прав (middleware).
  · adminUsers.js – управление пользователями.
  · adminChannels.js – управление каналами (просмотр, блокировка, верификация).
  · adminComplaints.js – жалобы.
  · adminPayments.js – платежи и транзакции.
  · adminAnalytics.js – аналитика (статистика).
  · adminSettings.js – настройки площадки, реклама, объявления, страницы.
  · adminBackup.js – резервное копирование.
  · adminLogs.js – просмотр логов действий.
  · adminAdmins.js – управление администраторами (только для владельца).
· Создай middleware isAdmin и hasPermission(permission) для проверки прав.
· Подключи все маршруты в app.js по пути /api/admin.

3. Управление пользователями

· Реализуй GET /api/admin/users – список пользователей с пагинацией, фильтрацией (по email, имени, роли, дате регистрации), сортировкой.
· GET /api/admin/users/:id – детальная информация о пользователе (все поля, включая скрытые, историю платежей, подписки, жалобы на него и от него).
· PUT /api/admin/users/:id – редактирование пользователя (изменение email, имени, роли, блокировка/разблокировка, удаление аватара и т.д.).
· POST /api/admin/users/:id/block – блокировка пользователя (с указанием причины и срока, если нужно). В модели User добавить поля isBlocked, blockedReason, blockedUntil, blockedBy.
· POST /api/admin/users/:id/unblock – разблокировка.
· DELETE /api/admin/users/:id – удаление пользователя (мягкое или полное). Лучше мягкое: помечать как удалённого (поле deletedAt), скрывать из списков, но сохранять данные для истории.
· GET /api/admin/users/:id/payments – история платежей пользователя.
· GET /api/admin/users/:id/subscriptions – подписки пользователя.

4. Управление каналами (для админов)

· GET /api/admin/channels – список всех каналов (с пагинацией, фильтрацией по названию, владельцу, статусу верификации).
· GET /api/admin/channels/:id – детальная информация.
· PUT /api/admin/channels/:id – редактирование канала (изменение названия, описания, блокировка/разблокировка, смена владельца).
· POST /api/admin/channels/:id/block – блокировка канала (становится недоступен для всех).
· POST /api/admin/channels/:id/verify – принудительная верификация (если заявка уже одобрена, но можно и напрямую).
· DELETE /api/admin/channels/:id – удаление канала.

5. Обработка заявок на верификацию

· GET /api/admin/verification-requests – список заявок (пользователей и каналов) со статусом 'pending'. Фильтрация по типу.
· GET /api/admin/verification-requests/:id – просмотр заявки с документами.
· PUT /api/admin/verification-requests/:id – рассмотрение заявки:
  · Принимает status ('approved'/'rejected'), comment (опц.).
  · Если одобрено и это пользователь – установить isVerified: true у пользователя.
  · Если одобрено и это канал – установить isVerified: true у канала.
  · Записать, кто рассмотрел (reviewedBy), дату.
· Также можно добавить возможность запросить дополнительные документы (тогда статус 'pending' с комментарием).

6. Система жалоб

· GET /api/admin/complaints – список жалоб со статусом 'pending' (или все). Фильтрация по типу, статусу, дате.
· GET /api/admin/complaints/:id – просмотр жалобы с контекстом (например, если жалоба на сообщение – показать это сообщение и диалог).
· PUT /api/admin/complaints/:id – обработка жалобы:
  · Принимает status ('resolved'/'rejected'), resolution (текст), action (опционально – какие меры приняты: предупреждение, блокировка пользователя, удаление контента).
  · Если action включает блокировку или удаление, выполнить соответствующие действия (вызвать API блокировки пользователя или удаления сообщения).
  · Записать resolvedBy.
· Действия администратора логировать в AdminLog.

7. Управление платежами и тарифами

· GET /api/admin/payments – список всех платежей (с фильтрацией по пользователю, статусу, дате).
· GET /api/admin/payments/:id – детали платежа.
· POST /api/admin/payments/refund/:id – инициировать возврат (если платёжка поддерживает) – сложно, можно пока заглушку.
· GET /api/admin/products – список всех платных продуктов (стикерпаки, подписки, расширения).
· PUT /api/admin/products/:id – изменение цены, названия, активности продукта.
· POST /api/admin/products – создание нового продукта (например, новый стикерпак от проекта).

8. Аналитика

· Реализуй эндпоинты для получения статистических данных:
  · GET /api/admin/analytics/overview – общая информация: количество пользователей (всего, новых за день/неделю/месяц), количество каналов, бесед, сообщений, доход за период.
  · GET /api/admin/analytics/users – график регистраций по дням.
  · GET /api/admin/analytics/payments – график доходов по дням, распределение по продуктам.
  · GET /api/admin/analytics/activity – активность (сообщения, звонки) по дням.

9. Управление рекламой и объявлениями

· CRUD для рекламных блоков (AdBlock):
  · GET /api/admin/adblocks – список.
  · POST /api/admin/adblocks – создание.
  · PUT /api/admin/adblocks/:id – редактирование.
  · DELETE /api/admin/adblocks/:id – удаление.
· CRUD для объявлений на площадке (Announcement):
  · Аналогичные эндпоинты.
· На клиенте админ-панели нужно будет сделать формы для настройки.

10. Редактирование статических страниц

· CRUD для StaticPage:
  · GET /api/admin/pages – список страниц.
  · GET /api/admin/pages/:slug – получение содержимого.
  · PUT /api/admin/pages/:slug – обновление (принимает title, content).
· На клиенте можно использовать простой WYSIWYG-редактор (например, React Quill).

11. Настройки площадки

  · Проверяет с SecretCode.deleteCode.

  · Изменяет статус на 'archiving'.
  · Создаёт дамп базы данных (например, с помощью pg_dump командной строки) и сохраняет во временный файл.
  · Архивирует папку с загруженными файлами (например, uploads/) вместе с дампом в ZIP или tar.gz.
  · Загружает архив в облачное хранилище или сохраняет локально с уникальным именем.
  · Обновляет статус на 'sending' и отправляет email на valery_oborin@vk.com с ссылкой на архив (или прикрепляет, если размер позволяет). Для отправки email использовать nodemailer.
  · После успешной отправки статус 'completed'.
  · Затем выполняет необратимые действия: удаление всех файлов проекта (базы данных, загруженных файлов, кода?). Удаление кода сервера – это сложно и может быть опасно, поэтому можно ограничиться удалением базы данных и файлов, а код оставить, но проект станет неработоспособным. Также можно удалить все таблицы.
  · Для полного самоуничтожения можно выполнить команду process.exit() после всего, но это не удалит код. На сервере можно запустить скрипт, который удалит сам себя. Это слишком сложно, поэтому пока ограничимся удалением данных.
· На клиенте:
